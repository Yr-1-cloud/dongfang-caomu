> 依据：对比表方案 5「多源一体化」（产品化方案，核心亮点"统一入口，扩展性最强"）+ 「后台管理」功能地图。

> 技术栈：Python 3.14.4 + uv + FastAPI 0.141.1 + uvicorn 0.53.0 + PyMySQL 1.2.0 + DBUtils.PooledDB 3.2.0 + MySQL 8.0.46（库 `tcm`）+ **原生 HTML/JS + Bootstrap 5.3.3 + axios 1.7.7（无构建工具）** + Chroma（collection `tcm_knowledge`）+ **本地 embedding / rerank 模型**（PyTorch 2.14.0+cpu / transformers / sentence-transformers / modelscope）+ DeepSeek。**纯设计，不含代码。**

## 一、总体架构

**B/S 架构 Web 应用（无构建工具）**，交付形态为浏览器访问，自上而下四层：

```
前端表现层  static/          原生 HTML/JS + Bootstrap 5.3.3 + axios 1.7.7
  ├── static/common/        公共资产（css / js vendor / js core）
  ├── static/admin/         后台页面 + 9 个业务脚本（HTML 片段）
  ├── static/rag/           知识库页面
  └── static/qa/            智能体型独立页（完整 HTML 页）
        ↓ HTTP /api/**    Authorization: Bearer <token>
API 层      com/tcm/<模块>/api.py      路由注册、入参接收与校验、挂鉴权依赖 require_perms(...)、统一响应 {code, msg, data}
业务层      com/tcm/<模块>/service.py  业务规则、事务编排、数据权限条件拼装 build_data_scope()、树结构组装 build_tree()
数据层      com/tcm/<模块>/dao.py      SQL 拼装（全部 %s 参数化；表名 / 列名走白名单）
           com/tcm/db/conn.py        连接池 + query_one / query_all / execute / insert
           com/tcm/db/tcmdb.py       存量业务表查询（TcmDb）
        ↓ PyMySQL 1.2.0（经 DBUtils.PooledDB 3.2.0 连接池）
        MySQL 8.0.46 · 库名 tcm · 30 张表 · utf8mb4 / utf8mb4_general_ci / InnoDB
```

**三个子系统**（范围划分，对应 `static/` 三个目录）：

| # | 子系统 | 代码位置 | 前端位置 | 状态 |
|---|---|---|---|---|
| 1 | 后台管理系统 | `com/tcm/system/` | `static/admin/` | ✅ 已完整实现并验证通过 |
| 2 | 知识库构建（RAG） | `com/tcm/rag/` | `static/rag/` | 🟡 已设计，待实现 |
| 3 | 智能体问答（QA） | `com/tcm/qa/` | `static/qa/` | 🟡 已设计，待实现 |

**产品价值定位**：先把中医药存量资料管理起来 → 再把资料加工为知识库 → 最后在知识库之上提供自然语言问答。

三个子系统**共享同一份 knowledge 表与同一份向量库**（Chroma，collection `tcm_knowledge`），这是方案 5"统一入口"的体现。

## 四、前端设计

**实现方式**：原生 HTML/JS + Bootstrap 5.3.3 + axios 1.7.7，**无构建工具**（不引入 Node 工具链，交付即可部署）。页面按 `static/` 三个目录组织——`static/admin/`（后台页面 + 9 个业务脚本，HTML 片段）、`static/rag/`（知识库页面）、`static/qa/`（问答独立页，完整 HTML）、`static/common/`（公共 css/js）。axios 统一封装拦截器：集中注入 token、统一处理 401。

### 4.1 布局（三段式，简约的来源是规范而非设计感）

- **左侧菜单**：两级，宽度固定 200px，可折叠
- **顶部栏**：面包屑 + 用户下拉（个人信息/退出）
- **内容区**：白底卡片，统一内边距 20px，**每个页面只有：搜索区 + 操作栏 + 表格（+ 分页）**

### 4.2 页面统一骨架（所有模块共用，这是"简约美观"的关键）

1. 搜索区：一行表单（关键词 + 状态下拉 + 查询/重置），可折叠
2. 操作栏：左侧主操作按钮，删除等危险操作用次要样式 + 二次确认
3. 表格：固定表头、操作列右对齐、空状态有提示、加载有骨架
4. 弹窗：新增/编辑用 Dialog + 表单校验，错误提示在字段下方
5. 反馈：成功用轻提示，失败提示要带原因

**统一规范**：间距只用 8/16/20/24；主色一个；中性色三档；圆角统一；字号三档（标题/正文/辅助）。9 个页面长得一样，视觉自然整齐。

## 五、后端设计

### 5.1 分层（四层，职责单一）

```
API 层    com/tcm/<模块>/api.py      路由注册、入参接收与校验、挂鉴权依赖 require_perms(...)、统一响应 {code,msg,data}
业务层    com/tcm/<模块>/service.py  业务规则、事务编排、数据权限条件拼装 build_data_scope()、树结构组装 build_tree()
数据层    com/tcm/<模块>/dao.py      SQL 拼装，全部 %s 参数化；表名 / 列名走白名单
        com/tcm/db/conn.py        连接池 + query_one / query_all / execute / insert
        com/tcm/db/tcmdb.py       存量业务表查询（TcmDb）
```

- API 层只收参数与返回包装，不写业务；业务层不写 SQL；**SQL 全集中在数据层，一律 `%s` 参数化，表名列名走白名单**
- ⚠️ **路由用 `def`，不用 `async def`**（架构约束）：连接池是同步的，在 `async def` 里做同步数据库调用会**阻塞事件循环**。要做 SSE 流式输出，用**同步 generator + `StreamingResponse`** 即可，不必把路由改成 async
- ⭐ **必须用连接池**：一次 `connect()` 要做 TCP 握手 + MySQL 认证，毫秒级开销看着小，但**每个请求都建连会成为瓶颈**，还会打满 MySQL 的 `max_connections`（新请求直接被拒）；异常路径忘记 `close()` 还会泄漏连接。选定 `DBUtils.PooledDB 3.2.0` 包住 PyMySQL。Notebook/脚本一条长连接即可，**FastAPI 多线程场景必须池化**（或至少每次操作新建 + 用完关闭）。两个注意：连接不能跨进程共享（多进程时总连接数 = 进程数 × 池大小）；MySQL 默认 8 小时无活动断开，池要配 ping 检测或重连策略，否则拿到死连接

### 5.2 统一响应与异常

所有接口返回 `{code, msg, data}`，分页带 `total`。异常统一捕获转友好提示，**原始堆栈进操作日志**——前端看不到 traceback，日志里能看到。

### 5.3 鉴权与权限 🔴

- 登录 → 校验哈希密码 → 签 JWT → 前端带 token → 中间件统一校验
- 权限校验链路：当前用户 → 角色 → 菜单/按钮权限码 → 判断能否调该接口
- **两处都要校验**：前端控制按钮显示只是体验，后端不校验等于没有权限

### 5.4 日志怎么记 🔴

- **操作日志**：用装饰器/中间件统一记录（谁/何时/哪个接口/什么参数/耗时/成败/异常）。**不要每个函数手写插入**，会漏且脏
- **登录日志**：登录接口单独记，成功失败都记（失败记录才是审计价值）
- **问答日志**：RAG 图跑完后写一条（问题/命中条数/来源分布/耗时/是否命中），既是统计也是调优依据
- 三类日志只追加不修改，页面只读，支持按时间清理

### 5.5 数据表设计 🔴

统一规范：每表带创建人/时间、更新人/时间、备注；**删除一律软删（del_flag）**，与知识库的 isDel 语义一致。系统表用 `sys_` 前缀与业务表分离。

| 表                             | 关键字段                                      |
| ----------------------------- | ----------------------------------------- |
| sys_user                      | 用户名、密码哈希、昵称、手机、邮箱、部门id、状态、最后登录时间、del_flag |
| sys_role                      | 角色名、权限标识、数据范围、排序、状态                       |
| sys_dept                      | 父id、部门名、排序、负责人、状态（树形）                     |
| sys_menu                      | 父id、菜单名、路由、组件、权限标识、类型、图标、排序、可见            |
| sys_dict_type / sys_dict_data | 字典类型 → 字典项（标签/值/排序）                       |
| sys_attachment                | 原文件名、存储名、路径、大小、类型、来源模块、上传者、**解析状态**、**file_md5（秒传去重，唯一约束）** |
| sys_config                    | 参数名、参数键、参数值、是否内置（含分类置信度阈值，见 6.5）        |
| knowledge（统一知识表）             | source、src_fid、title、content、category、summary、keywords、state、isDel、**review_status / vector_status（见 6.2）**、**confidence / classify_reason（见 6.5）** |
| sys_login_log / sys_oper_log  | 见 5.4                                     |
| sys_vector_task 🟡            | 任务类型（全量/增量/单条）、状态、进度、失败原因                 |
| qa_log                        | 问题、命中条数、来源分布、耗时、是否命中                      |
| 关联表                           | user_role、role_menu                       |

## 六、知识库管理（图的重点，也是方案 5 的核心）

### 6.1 结构化 vs 非结构化并存 🔴

- **结构化进 MySQL**：原始三表原样导入不动；清洗结果写统一 `knowledge` 表（source + src_fid 溯源、title、去 HTML 的 content、category、summary、keywords、state、isDel），(source, src_fid) 唯一约束保证可重跑
- **非结构化进 Chroma**：切片向量 + 元数据（source/src_fid/title/段落类型）
- **为什么并存**：字段筛选是 SQL 主场，语义命中是向量主场——**协同，不是替换**。管理页操作 MySQL，向量化动作同步更新 Chroma

### 6.2 知识录入与状态机（手动）🔴

就是 Web 版的知识表增改：新增/编辑表单（标题、来源、分类、关键词、摘要、正文）。

**知识状态机**（对齐参考系统的「结构化数据」页，两个状态字段分开看、分开展示）：

| 字段 | 取值 | 谁来改 |
|---|---|---|
| `review_status` 复核状态 | 待复核 → 已复核 / 已拒绝 | 分类动作 + 人工复核 |
| `vector_status` 向量状态 | 未入库 → 已入库 / 失败 | 向量化动作 |

**入库门禁**：**只有"已复核"的知识才允许向量化进 Chroma**——人工把关质量，脏知识进不了检索库。"全量向量化"按钮同理，**只跑已复核的记录**。

**⭐ 门禁不能把 3.7 万存量卡死**（关键设计点）：清洗导入的存量知识来自已有结构化表，本身可信 → **存量自动复核通过**；**复核门禁只对"新产生"的知识生效**——手动录入默认"已复核"（录入人自己负责），上传文档解析出的知识默认"待复核"，人工通过后才入库。

编辑保存后的联动不变：改的是已入库的知识 → 触发该条重算向量；未入库的只改 MySQL。"不做同步，admin 就是个摆设"仍然成立。

### 6.3 向量化：全量 + 增量 🔴

以下四个问题，落成管理端的四个可配置项：

1. **数据怎么加载、切割、向量化** → 从 knowledge 表分批读 → 按 HTML class 段落切 → 过 embedding 模型 → 写 Chroma（全量按钮 = 跑一次这个流程）
2. **向量模型选择** → 参数配置页存模型名：**embedding `bge-large-zh`、rerank `Qwen3-Reranker-0.6B`**；**换模型 = 语义空间变化 = 必须全量重跑**，参数页要写清提示。CPU 实测精排卡顿 > 3 秒时，再降级为 `bge-reranker-v2-m3`
3. **重排模型** 🟡 → 精排上线后再配（一期不启用）
4. **LLM 选择** → 参数配置页存（DeepSeek），问答端读取

**增量**：单条编辑/新增后更新该条向量；批量导入后按 source 增量补。管理页要给"向量化状态"字段（未向量化/已向量化/失败），失败可单条重试。

### 6.4 资料管理（附件上传 → **统一转 PDF** → 解析入库）🟡

便签写的增量知识来源：word/excel/ppt/pdf/doc/csv/tsv。**明确要求：上传后统一转成 PDF**，再走解析。

**为什么要统一**（好处确实成立）：
1. **解析链路只需维护一条**——下游只对接 PDF 解析器（PyPDFLoader / MinerU），不用为每种格式写一个 Loader 并各自调试
2. **存储与预览格式统一**——附件只有一种"标准件"，列表页预览、下载、归档逻辑都简单
3. **职责边界清晰**——转换环节负责"转成 PDF"，解析环节负责"解析 PDF"，接口只有一个

**⭐ 三条必须做的补救**（统一转 PDF 的风险都在转换这一步，不兜住会真出问题）：

> 📌 **要求：所有上传的文件都转 PDF**（含 csv/tsv/txt/md，不只办公文档）。按此执行，并配两条自动保险。

| 风险 | 补救（自动执行，不需要人工判断） |
|---|---|
| **转换会失败**（加密文件、缺字体、LibreOffice 崩、超大文件） | **保留原文件**不动；转换失败 → 状态标"转换失败" → **降级用原格式 Loader 直接解析**，不让用户白传一次 |
| **⭐ 转换后文本丢失**（尤其表格：csv/xlsx 转 PDF 再解析会丢行列分隔符；这是"全转"最大的隐患） | **文本可逆校验**：转换并解析后，比对解析出的文本长度与原文件文本长度（纯文本类可直接比对字符重合度）。**若抽取文本 < 原文的 50%，自动回退用原格式直接解析**，并在解析状态里记明原因。这条既满足"全转"，又保证质量不崩 |
| **重复解析烧成本** | **解析结果缓存**：PDF 解析出的 md 写回磁盘，下次直接读，不重复调 MinerU |

**表格类的补充建议**（不冲突，可同时做）：即使按要求转了 PDF，**表格类（csv/xlsx）仍建议同时用原文件做一次结构化直读**（CSVLoader + 表头拼进每行），因为结构化直读的行列关系远比 PDF 抽取准确。两者取质量更好的那份入库。**这条可以先按"全转"做，后续可按需调整是否只保留 PDF 一条路。**

**转换实现**：跨平台用 **LibreOffice 无头模式**（`soffice --headless --convert-to pdf --outdir ...`）；Windows 若装了 Office 也可用 `docx2pdf`。转换服务要设**超时**与**重试**，并把转换结果路径写回 `sys_attachment`。

**落地节奏**：

- **一期（🔴 半成品）**：附件能上传、能存、能管（sys_attachment 表 + 来源模块 + 转换状态 + 解析状态字段），转换与解析动作先不做
- **后续（🟡）**：上传 → 统一转 PDF（失败则降级）→ 解析成文本 → 写 knowledge 表（source 标为"上传"）→ 自动向量化 → 更新状态

**表结构配套**（`sys_attachment` 新增两列）：`convert_status`（未转换/已转换/转换失败）、`converted_path`（转换后 PDF 路径，原文件字段仍保留原格式）

**去重配套**：`sys_attachment` 增加 `file_md5` 列并建唯一约束——上传时先算 MD5 查重，命中即"秒传"（直接复用已有记录与解析结果，不存两份、不重复解析）。这与 3.3 的"切片内容哈希幂等"是同一思想，两层各管各的：MD5 管文件层，切片哈希管向量层。

### 6.5 分类复核：LLM 辅助分类 + 置信度 + 人工确认 🟡（字段一期预留）

参考智能知识库系统的「分类复核」页，吸收四个设计：

1. **LLM 自动分类，带置信度与理由**：对没有类目的知识（方剂/药材源 `category` 为空），用 LLM 按分类树打标（如"偏方大全 > 内科"），同时给出**置信度（0-100）与理由**。**源数据自带类目的直接 confidence=100，理由写"源数据自带类目 (tcm_pianfang.channelId)"，自动通过**——这正好补上方案里"category 另两源留空"的缺口。
2. **复核列表按置信度升序**：最不可信的排最前面，人工精力花在刀刃上；列表展示"标题/内容、类型、LLM 判定（分类树）、置信度、理由"。
3. **三种处置**：**通过** → 写入向量库（进检索库）；**改类目** → 人工指定正确分类后再通过；**拒绝** → 撤销整条记录（软删），永不入库。顶部提供**批量分类**按钮（对筛选出的未分类记录批量跑 LLM）。
4. **与门禁衔接**：LLM 分完类的记录仍进"待复核"，由 6.2 的门禁决定是否入库；置信度阈值（如 ≥90 自动通过）放参数配置页，可调可关。

表结构配套（`knowledge` 新增四列，**一期建表就带上**，功能二期实现）：

| 列 | 说明 |
|---|---|
| `review_status` / `vector_status` | 复核状态 / 向量状态（见 6.2） |
| `confidence` INT | LLM 分类置信度 0-100，自带类目 = 100 |
| `classify_reason` VARCHAR | 判定理由（如"源数据自带类目 (tcm_pianfang.channelId)"） |

## 十、踩坑预警

1. **pymysql 必须 utf8mb4**，建库/建表/连接三处一致，少一处中文变问号
2. **密码必须哈希**，明文是安全红线也是必查项
3. **SQL 一律参数化**，拼接是硬伤
4. **软删要贯彻**：所有查询默认带未删除条件，否则"删了还能查到"
5. **权限两处校验**：前端只管显示体验，后端才是安全
6. **树形模块删除前校验子节点**，否则产生孤儿
7. **向量化同步别忘**：后台改了知识不重算向量，问答端答的永远是旧数据——**这是最容易翻车的联动**
8. **前端 hash 路由**：避免部署后刷新 404
9. **日志表只增不改**，要能按时间清理，否则日志表自己先撑爆
10. **换 embedding 模型 = 全量重跑**，参数页要写清提示，避免半新半旧
11. **FastAPI 里不用连接池**：请求一多打满 `max_connections` 新请求被拒；异常路径漏 `close()` 会泄漏连接（见 5.1）
12. **长连接被 MySQL 断开**：默认 8 小时无活动断开，池必须配 ping/重连，否则拿到死连接
13. **统一转 PDF 后没有兜底**：转换会失败（加密文件、缺字体、LibreOffice 崩），必须保留原文件 + 降级用原格式 Loader 解析（见 6.4）
14. **表格类也跟着转 PDF**：csv/xlsx 转 PDF 再解析会丢行列关系，表格与纯文本应跳过转换直接解析，并把表头拼进每行
15. **重复解析同一份 PDF**：MinerU 解析结果要写回磁盘缓存，否则重跑一次烧一遍额度
14. **把路由写成 `async def` 却在里面做同步 DB 调用**：会阻塞事件循环（架构约定"路由用 def 不用 async def"）；流式输出用同步 generator + `StreamingResponse` 即可
15. **前端引入构建工具**：Node 工具链会让"交付即可部署"变成"先构建再部署"，增加运维成本；本项目统一用原生 HTML/JS + Bootstrap + axios
16. **前端把 `static/` 三目录混放**：页面按 `admin / rag / qa` 分开，公共资产进 `common`，否则三个子系统互相污染
17. **复核门禁别把存量卡死**：3.7 万条存量若全部标"待复核"等人工点通过，一期根本演示不了——**存量自动复核通过，门禁只对新产生的知识生效**（见 6.2）
18. **复核状态与向量状态必须联动**：拒绝/禁用一条已入库知识时，要同步把它的向量从 Chroma 删掉，否则"拒绝了还能检索到"（与踩坑 7 同源，方向相反）
19. **MD5 去重要在建表时就加唯一约束**，后补约束碰到已有重复文件会建失败；MD5 计算放在存盘之前，别传完再算
